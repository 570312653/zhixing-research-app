# 知行项目工作系统审计与后续总路线（讨论稿）

> 状态：讨论稿，不是实施授权  
> 审计日期：2026-08-01  
> 审计范围：项目本地 `_system/`、正式文档、StarWork 多岗位状态、报告引擎、历史 POC 隔离、Android 工程准备度。  
> 写入边界：本次只新增本讨论稿；未修改 `_system/`、业务代码、外部服务、密钥、云端配置或 Android 环境。

## 1. 审计结论

项目当前**不能直接进入 Android 工程初始化**。

原因不是报告引擎失效，而是 2026-08-01 刚完成“多人 Web 应用 → 个人 Android APK”的产品路线切换，工作系统和部分辅助文档尚未同步；客户端的详细 UI、所有者认证、云端架构、iFind 技术适配及 Android 构建环境也尚未完成阶段性确认。

同时也有明确的健康基础：

- StarWork 工作台 `strict_ok=true`，工作台类型、正式文档区、过程区和四个多 Agent 岗位结构均有效；无需重建或升级。
- `report-engine` 当前 124/124 测试通过，TypeScript 构建通过。
- 报告引擎源代码未发现真实网络、环境变量、Coze、Vercel 或 Supabase 调用；检出的 URL 均是固定样例与安全测试数据。
- 已完成 `morning_scan`、`midday_review`、`daily_review`、`industry_tracking` 四类离线报告，以及共享 HTML/手机卡片/A4 打印样式。

## 2. 必须先解决的状态不一致

### P0：项目本地工作系统落后于正式文档

以下 `_system` 文件仍写着旧的多人 Web 与企业级数据源询价路线：

- `_system/context/current-projects.md`
- `_system/tasks/todo.md`
- `_system/context/decisions.md`
- `_system/diary/2026-07-31.md`（历史日志本身可以保留，但不能再充当当前路线）

正式事实已经变为：个人 Android APK、单一所有者、不开放注册；iFind 是个人主数据候选。恢复工作时虽然 `docs/current-status.md` 优先级更高，但长期不清理会让后续 Agent 误读待办。

建议：用户确认本审计后，单独执行一次项目本地存档同步，只做最小增量，不修改历史日记原文。

### P0：已确认的变更提案仍显示“待确认”

`docs/proposals/2026-08-01-personal-android-apk-change-proposal.md` 已被用户确认，但文件状态和七个复选框仍显示未确认。正式产品与架构文档已经更新，提案自身应改成“已确认并同步”，否则审计链自相矛盾。

### P1：Obsidian 辅助导航过期

以下辅助页仍把产品描述为多人 Web 应用，或仍显示旧报告数量和旧测试数：

- `docs/obsidian/项目导航.md`
- `docs/obsidian/决策与风险.md`
- `docs/obsidian/开发日志.md`

它们不是正式事实源，但容易误导人工浏览。建议在正式状态同步后一次性修正。

### P1：多 Agent 结构健康，但过程记录不可用

- 四个岗位已注册，StarWork 诊断通过；无需创建新岗位。
- 四份 lane `worklog.md` 仍是“待补充”空模板。
- `.starwork/handoff/state.json` 当前没有活动交接项。
- `_system/collaboration/shared.md` 只记录了 2026-07-29 的旧请求，没有 APK 路线的共享结论。

结论：岗位可以继续使用，但在新任务派发前，应先生成一个完整的 APK/UI 工作包，再一次性分发给规格、开发、安全和协调岗位。不要逐条同步访谈答案。

### P1：`AGENTS.md` 历史内容过长

顶部 0.2 节已经明确覆盖旧的多人 Web 与 Coze 路线，所以规则优先级没有实质错误；但同一文件仍保留大量旧 Coze POC、旧路线图和过期“下一步”，已使 StarWork doctor 产生路径误判警告，也增加 Agent 误读概率。

短期不删除历史内容。后续可以单独设计“历史审计内容迁移”方案：保留证据、修复链接、压缩 `AGENTS.md` 当前规则入口。未经预览与确认不得移动。

## 3. 工程准备度问题

### Android 工具链尚未具备

只读检查结果：

- Node.js：已安装（v24.18.0）
- npm：已安装（11.16.0）
- Java/JDK：未发现
- Android SDK 环境变量：未设置
- ADB：未发现
- Gradle：未发现
- Android 客户端工程：尚不存在

因此即使立即创建 Capacitor 源码，也无法在当前环境完成 Android 构建和真机安装验收。环境安装应放在 UI 设计确认和实施计划批准之后，避免提前引入大体积依赖和环境变更。

### 尚未建立 Git 仓库

项目根目录没有 `.git`。在开始新增 Android 客户端前，应确认：

- 是在当前目录初始化 Git，还是连接已有 GitHub 仓库；
- 历史 POC、`node_modules`、构建产物、临时 PDF 截图和敏感文件应如何忽略；
- Android 签名证书绝不能提交到仓库。

### 历史 POC 中存在敏感文件候选

发现 `phase1-webhook-test/.env.local`，本次没有读取或展示其值。该目录已被定义为历史 POC，但在建立 Git、共享目录或归档前，必须检查该文件是否仍包含有效凭证；如可能有效，应先轮换，再决定本地安全保留或清理。不得直接复制进新客户端工程。

## 4. 产品与设计尚未确认的事项

### 必须在客户端实现前确认

1. 主导航：底部导航使用哪些一级入口，页面之间如何返回和跳转。
2. 今日报告：首页卡片、生成状态、延迟/失败状态和行业摘要如何布局。
3. 报告库：日期、类型、行业/主题筛选在手机上的交互方式。
4. 行业与标的池：同一一级入口还是两个独立入口；趋势和历史变化如何展示。
5. 个人操作页：允许查看哪些任务信息，哪些操作需要二次确认。
6. 品牌视觉：App 图标、启动页、主色、字体、卡片与状态色。
7. 离线行为：无网络时是只显示缓存报告，还是明确阻止访问。

现有 `docs/superpowers/specs/2026-08-01-personal-android-apk-client-design.md` 只完成页面范围与组件边界，**尚未完成具体 UI/UX**，状态仍是待用户审阅。

### 可以在后续阶段再确认

- 单一所有者的登录方式；
- Vercel/Supabase 是否继续作为正式云端组合；
- iFind MCP 的云端自动调用方式、字段和配额；
- 模型供应商与模型调用契约；
- 正式 PDF、云端私有存储与短时下载；
- 正式 APK 签名、二维码下载页和更新策略；
- 是否需要 Android 系统通知。

这些问题不应阻塞离线 UI 原型，但必须在相应阶段开始前形成独立规格。

## 5. 推荐的完整工作流程

```text
阶段 0：工作系统收口
  → 阶段 1：客户端信息架构与 UI 原型
  → 阶段 2：客户端设计规格确认
  → 阶段 3：详细实施计划与工程准备
  → 阶段 4：离线 Android 客户端与调试 APK
  → 阶段 5：iFind 数据适配器技术验证
  → 阶段 6：单一所有者云端后端与私有归档
  → 阶段 7：真实报告生成、PDF 与自动调度
  → 阶段 8：正式签名 APK 与二维码交付
  → 阶段 9：个人稳定运行验收
```

## 6. 分阶段任务、交付与门槛

### 阶段 0：工作系统收口

主要任务：

- 同步 `_system` 当前项目、待办和决策；
- 把已确认的 APK 变更提案标为完成；
- 更新 Obsidian 导航；
- 登记 APK/UI 新工作包，清空旧的活动任务语义；
- 只记录历史 POC 敏感文件风险，不展示其内容。

交付：一致的恢复上下文和唯一当前待办入口。  
验收：从 `AGENTS.md`、`docs/current-status.md`、`_system/context/current-projects.md` 和 `_system/tasks/todo.md` 得到相同的下一步。

### 阶段 1：客户端信息架构与 UI 原型

主要任务：

- 集中确认所有页面、导航、状态与操作；
- 先完成低保真线框，再完成高保真手机界面；
- 保留现有报告正文视觉，新增 App 外壳、列表、筛选、状态和空页面规范；
- 在浏览器中生成可点击/可浏览预览，不建立 Android 工程。

交付：页面地图、关键用户流程、手机端原型、视觉组件规范。  
验收：用户逐页确认；正常、加载、空、失败、离线五类状态均有明确表现。

### 阶段 2：客户端设计规格确认

主要任务：

- 把阶段 1 结论合入客户端设计规格；
- 定义 AppShell、导航、数据仓库接口、页面输入输出和错误语义；
- 安全岗位复核 APK 无密钥、无隐式网络、无伪成功。

交付：最终客户端设计规格。  
验收：用户明确批准；不存在 TBD、相互矛盾或超出离线切片的能力。

### 阶段 3：详细实施计划与工程准备

主要任务：

- 生成文件级、测试级实施计划；
- 确认 Git/GitHub 路线和 `.gitignore`；
- 安装并验证 JDK、Android Studio/SDK、ADB；
- 确认 Android 应用 ID、最低系统版本、调试包名与构建方式。

交付：可执行计划、环境检查记录、干净的版本控制边界。  
验收：空白 Android/Capacitor 工程可构建调试 APK，但尚不实现业务页面。

### 阶段 4：离线 Android 客户端与调试 APK

主要任务：

- 实现 App 外壳、导航、五个页面和固定样例仓库；
- 复用已确认的报告 HTML 视觉；
- 所有未来网络操作明确禁用；
- 构建并安装调试 APK。

交付：本地调试 APK、安装说明、界面与回归测试报告。  
验收：真机安装、启动、导航、筛选、报告阅读无横向溢出；报告引擎回归继续 124/124 通过；包内无真实密钥和网络地址。

### 阶段 5：iFind 数据适配器技术验证

主要任务：

- 只验证个人 MCP/接口是否能由可信服务端自动调用；
- 建立字段、时区、配额、超时、证据和错误契约；
- 使用隔离测试环境和最小样例，不进入 APK。

交付：数据适配器技术报告与正式契约草案。  
验收：至少覆盖交易日历、早盘、午盘、复盘和行业跟踪所需字段；失败时可验证地关闭，不由模型补写。

### 阶段 6：单一所有者云端后端与私有归档

主要任务：

- 确认并建立服务端、认证、私有数据库/存储；
- 实现所有者会话、只读报告 API、受限任务操作 API；
- 密钥仅存服务端受控环境变量。

交付：受保护的开发环境 API 和私有报告归档。  
验收：未登录、错误账户和复制 APK 均无法读取报告；日志不泄密；RLS/权限测试通过。

### 阶段 7：真实报告生成、PDF 与自动调度

主要任务：

- 数据证据标准化后再调用模型；
- 接入版本化报告校验、正式 HTML/PDF、幂等、重试和告警；
- 按交易日与各报告时点调度。

交付：真实但仅所有者可见的自动报告链路。  
验收：连续运行、失败关闭、无重复、延迟可追溯；PDF 失败不影响 HTML。

### 阶段 8：正式签名 APK 与二维码交付

主要任务：

- 生成并离线备份签名证书；
- 构建 release APK；
- 建立 HTTPS 下载页与二维码；
- 验证覆盖升级与回滚说明。

交付：正式 APK、二维码、安装与升级说明。  
验收：真机从二维码完成下载、安装、登录和更新；签名证书、密钥与管理接口不暴露。

### 阶段 9：个人稳定运行验收

主要任务：

- 连续观察交易日任务、阅读、归档、失败和恢复；
- 修复严重问题并建立备份、恢复和版本记录。

交付：稳定运行报告与维护手册。  
验收：连续 10 个 A 股交易日无漏生成、重复报告或错误事实发布；异常可以定位和重试。

## 7. 推荐的当前下一步

不要初始化 Android 工程。先依次完成：

1. 用户确认本审计结论和阶段顺序；
2. 执行阶段 0 的项目本地状态同步；
3. 进入阶段 1，集中完成客户端信息架构和 UI/UX 访谈；
4. 生成手机端原型供用户逐页审阅；
5. UI 和设计规格获批后，才生成阶段 3 的代码实施计划。
