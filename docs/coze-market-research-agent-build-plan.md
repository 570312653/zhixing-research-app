# 知行市场研究 Agent：搭建与验收计划（已归档）

> 状态：**归档，不再作为正式实施计划。**2026-07-28 的 Coze Coding 多报告 Agent 未通过验收：未取得真实数据、未验证交易日、会输出 Markdown/多份报告/违规交易建议，且项目无可验证的金融数据 Skill。不得部署、接入或继续迭代为正式报告主链路。  
> 最后更新：2026-07-28  
> 后续正式方案：[知行报告引擎架构](./report-engine-architecture.md)。本文件保留原始需求、Skill 候选清单和失败证据，供迁移时参考；其中所有“Coze 应执行”的表述均不再具有实施效力。

## 1. 目标与范围

创建一个可部署、可复用的“知行市场研究 Agent”。它负责生成六类非个人化市场研究产物，并先以 Coze 内部日程完成内容验证；后续正式应用接入时，应用可调用同一个 Agent，不重写报告逻辑。

本次只建设内容生产能力、非敏感研究上下文、HTML 和 PDF 产物及验证用日程。**不**接入用户、持仓、交易记录、通知、数据库、正式报告归档、Vercel Cron 或真实用户发布。

## 2. 已确认的产品决定

| 项目 | 已确认决定 |
|---|---|
| Agent 形态 | 一个可部署的多报告 Agent，而不是六个孤立 Agent。 |
| 报告范围 | 早盘、午间小复盘、每日复盘、行业跟踪、节假日信息、月末复盘。 |
| 交易日 | 早盘、午间、每日复盘和行业跟踪仅在 A 股实际交易日运行。 |
| 节假日 | 周末和法定假日均在连续休市最后一天 20:00 生成节假日信息报告。 |
| 月末 | 每月最后一个 A 股交易日 20:30 生成非个人化月末复盘。 |
| 隐私边界 | 不读取或上传用户持仓、交易、操作记录、个人偏好或其他个人数据。 |
| 报告阅读 | 先生成 HTML 正文，再通过 Playwright + Chromium 导出 PDF。HTML 是默认阅读内容，PDF 是附件。 |
| 推送与归档 | 本轮不使用旧 `sync_to_app.py` 作为正式交付链路；正式接入由未来知行应用统一处理。 |
| 文案边界 | 不承诺收益，不给个性化交易指令；“推荐”统一转为研究观察、条件式跟踪和具体风险说明。 |

## 3. 推荐实现方案与原因

### 3.1 方案比较

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 一个多报告 Agent + 六个日程 | 模板、来源规则、版本、风险提示和输出契约统一；后续易被应用 API 复用。 | Prompt、路由和日程并发控制需要设计清楚。 | **采用。** |
| B. 六个独立 Agent | 每类报告相互隔离。 | Skill、规则、版本和修复会重复六次，报告间的复盘验证难共享。 | 不采用。 |
| C. 现在直接由未来应用 Cron 调度 | 最符合正式长期架构。 | 正式应用、数据库与权限尚未建立，当前会阻塞内容验证。 | 后续阶段采用，不作为本轮前置条件。 |

### 3.2 核心原则

- Agent 通过 `report_type` 和受控任务参数路由到对应模板；不根据自由文本猜测日程类型。
- 每一类报告使用独立的内容模块和质量检查，但共享数据来源优先级、安全规则、版本策略和风险提示。
- 前一日复盘与当日早盘的判断验证，使用非个人化的“市场判断台账”，不依赖临时 Session 记忆或用户操作记录。
- Coze 内部 Calendar 仅用于内容生成验证和草稿产物；正式用户归档、通知和发布仍属于未来知行应用。

## 4. 日程与报告定义

所有时间采用 `Asia/Shanghai`。每个 Calendar 任务设置 `time_range`：开始时间前 10 分钟到后 40 分钟，避免整点资源高峰导致静默跳过。

| 日程 | `report_type` 提案 | 调度窗口 | 运行条件 | 核心内容 |
|---|---|---|---|---|
| 早盘扫描 | `morning_scan` | 08:20–09:10 | A 股实际交易日 | 盘前定价、隔夜市场、A 股映射、新闻公告、主线、资金与风险日历。 |
| 午间小复盘 | `midday_review` | 11:50–12:40 | A 股实际交易日 | 上午行情和异动；验证前一日复盘与当日早盘中的可验证判断。 |
| 每日复盘 | `daily_review` | 17:20–18:10 | A 股实际交易日 | A 股收盘结构、板块与资金、主线、标的池变化、次日观察。 |
| 行业跟踪 | `industry_tracking` | 19:50–20:40 | A 股实际交易日 | 十五五赛道趋势、催化、异动、行业研究更新和观察标的池。 |
| 节假日信息 | `holiday_digest` | 19:50–20:40 | 连续休市最后一天 | 高价值政策、宏观、产业、公司与海外信息，供下一交易日前观察。 |
| 月末复盘 | `month_end_review` | 20:20–21:10 | 每月最后一个 A 股交易日 | 非个人化的市场、行业、风格与主线归因，以及下月观察框架。 |

### 4.1 并发风险

每月最后一个交易日，20:00 行业跟踪与 20:30 月末复盘的窗口会重叠。创建日程前必须验证 Coze 是否为同一 Agent 提供独立 Session 和稳定的并发执行能力。

- 若并发通过：按上表执行，两个报告互不读取对方未完成产物。
- 若并发不通过：不得悄悄串行或覆盖文件；暂停日程创建，优先将月末复盘调整到 21:00，并提交给用户确认。

### 4.2 A 股交易日判断

日程触发后必须先判断当日是否为 A 股实际交易日，不能简单使用“工作日”。需要采用可核验的交易所/权威市场日历来源，并输出结构化结果：`is_trading_day`、`calendar_source`、`checked_at`。

- 非交易日：四类交易日报告不生成，也不产生空 PDF。
- 连续休市最后一天：只生成 `holiday_digest`。
- 月末复盘：只在当月最后一个实际交易日生成；节假日不按自然月最后一天误触发。

## 5. 每类报告的内容要求

所有报告必须遵守 [Coze 报告内容输出标准](./coze-report-output-standard.md)：标题带日期和版本、3～5 条摘要、完整 HTML、真实来源、数据截至时间、生成时间以及固定风险提示“仅供信息参考，不构成投资建议”。

### 5.1 早盘扫描

沿用交接文档的十模块：盘前定价信号、外围夜盘与美股 A 股映射、大宗商品、隔夜新闻与公告、热门板块、主线分析、前日盘面信号、关键点位、资金面和国际事件。

早盘中的“策略”只能写为需要跟踪的条件、风险和验证点；不得给出对具体用户的买卖、仓位或止损指令。

### 5.2 午间小复盘

这是新增报告类型，应包含：

1. 上午主要指数、量能、板块和异动概览；
2. 与早盘扫描一致或背离的市场信号；
3. 对前一交易日每日复盘与当日早盘中可验证判断的逐条验证；
4. 下午仍需观察的变量、风险与事件；
5. 固定风险提示。

“验证”必须逐条引用原判断的日期和报告 ID，并标注 `已验证`、`部分验证`、`未验证` 或 `失效`，不能事后模糊改写原判断。

### 5.3 每日复盘

以 A 股为主体，沿用交接文档的市场定调、指数与分时、板块与资金、主线确认矩阵、涨停与连板、龙虎榜、资金面、核心关注标的池、次日观察的结构。

结论必须区分事实、推断和待验证事项。标的池写研究观察理由、风险和公开依据，不写“快买”“满仓”等指令。

### 5.4 行业跟踪

每日行业跟踪以交接文档的十六个十五五赛道为范围，输出赛道涨跌、资金、异动、催化、轮动和观察标的池变化。

为避免每天重复生成冗长调研，日报分两层：

- **每日跟踪层**：总览、异常预警、变化原因、赛道轮动、观察点和风险；
- **深度研究更新层**：仅在重大政策、技术路线、供需、业绩、产业链或监管变化时追加行业研究段落。完整行业深度研究仍遵循交接文档的五段式结构：核心结论、需求端、供给端/产业链、标的池评分分层、风险提示。

新建或更新深度研究前，先检查该赛道既有报告；有历史版本时更新并提升版本号，不重复创建同名首版。

### 5.5 节假日信息报告

采用非个人化市场研究版：筛选连续休市期间可能影响下一交易日的高价值国内外政策、宏观、行业、公司和海外市场信息，并说明发生时间、来源、可能影响和不确定性。

不包含持仓影响、持仓集中度、仓位偏离、盈亏分析或再平衡建议。

### 5.6 月末复盘

采用非个人化市场研究版：总结当月主要指数、风格、行业、主线、政策/宏观变量、市场判断验证和下月待观察事项。

不读取 `MEMORY.md` 中的个人操作、不分析个人盈亏、不输出交易归因、仓位或再平衡建议。

## 6. 数据来源与 Skill 规则

### 6.1 创建前必须核验

交接文档列出的 Skill 不因文档存在而自动可用。新 Agent 创建后，先核验其是否可安装、启用和稳定调用；缺少、改名、无权限或返回质量不达标时，记录缺口，不得以猜测替代。

### 6.2 来源优先级

1. 券商官方 Skill：`gs-stock-market-query`、`gs-stock-financial-query`、`hot-rank-news`、`gf-lhb-list`、`gf-stock-f10`、`gf-stock-valuation` 等。
2. 官方/权威宏观与市场数据 Skill：`frankfurter-data`、`fred-data`、`openecon-data`、`akshare-commodities-energy-skill`、`akshare-futures-options`、`eia-data-skill`、`imf-data`、`worldbank-data`、`bis-data-skill`。
3. 调研 Skill：`industry-trend-research`、`company-competitor-research`、`sector-hotness-analysis`、`tianyancha-data`、`institutional-opinion-summary`、`full-dim-stock-risk-radar` 等。
4. `search_web`：仅用于官方/券商 Skill 无法替代的个股公告、政府政策原文、国际重大事件、实时涨停/连板和时效性新闻；优先政府、交易所、公司与持牌媒体来源。
5. UGC 平台：只可作为情绪旁证，不得作为核心事实来源。

### 6.3 禁止与限制

- `ciccwm-market-analysis` 禁止使用。
- `stock-data-skill` 不进入本计划的六类报告。交接文档允许它仅用于未纳入本轮的胜率追踪，不能扩展使用。
- 禁止虚构 Skill、数据、新闻、公告、来源链接、评分或结论。
- 关键数据与结论必须标明来源、数据日期和不确定性。

## 7. 非个人化研究上下文与判断台账

午间验证、每日复盘和月末复盘需要跨日引用市场判断，但不能依赖临时 Session 或个人记录。Agent 应维护仅含公开市场研究信息的结构化台账：

```json
{
  "claim_id": "market-2026-07-23-morning-01",
  "source_report_id": "morning-2026-07-23",
  "source_report_type": "morning_scan",
  "claim_date": "2026-07-23",
  "claim_text": "可验证的市场判断原文",
  "validation_window": "same_day_pm",
  "status": "pending",
  "evidence_links": []
}
```

- 只记录可公开验证的市场判断、报告 ID、来源和验证结果。
- 不记录用户持仓、买卖、金额、身份、Cookie、Token、Prompt 或 `SECRET.md` 内容。
- 验证结果不得覆盖原判断；应新增验证记录并保留版本历史。
- 具体存储介质需在 Coze 能力核验后确定；优先使用 Agent 可控的非敏感持久工作区或受控数据表，不使用 `/tmp` 作为跨 Session 存储。

## 8. 产物、PDF 与交付格式

### 8.1 生成流程

```text
结构化研究数据
  → 内容校验
  → content_html
  → Playwright + Chromium 渲染 PDF
  → HTML、PDF 与结构化报告对象
```

- 禁止使用 reportlab 直接生成 PDF。
- 渲染前检查 HTML 安全标签白名单、中文字体和来源链接。
- PDF 失败不得伪造成功：保留 HTML 草稿、返回受控错误状态并记录可重试原因。
- 初期产物仅保存在 Coze 的受控工作区用于验收；正式应用接入后，HTML 和 PDF 进入受控应用存储，不使用旧脚本直接同步。

### 8.2 结构化输出提案

现有技术契约尚未覆盖本计划新增类型。正式 API 接入前，需要将允许枚举扩展为：

```text
morning_scan
midday_review
daily_review
industry_tracking
industry_research
holiday_digest
month_end_review
```

- `industry_tracking`：交易日 20:00 的赛道跟踪日报。
- `industry_research`：因重大变化触发的深度行业研究更新，或后续按需单独调用。
- `watchlist_snapshot` 继续作为独立 `delivery_type`，不嵌在报告正文中。
- 对新增枚举、午间验证对象和月末复盘对象，应在创建 Agent 前同步更新内容标准与技术契约，并提供样例。

## 9. Agent 创建步骤

### 第一步：创建前检查

1. 在 Coze 编程中确认项目类型可部署为 Agent API。
2. 审核当前可安装 Skill、模型权限、Calendar 能力、工作区持久化能力和 Playwright/Chromium 运行能力。
3. 确认没有引入 `SECRET.md`、明文 Token、用户数据或旧 `sync_to_app.py`。
4. 确认 A 股交易日历的权威来源与调用方式。

**通过条件**：能力清单有证据；缺失能力被明确记录；未以不安全的文件或临时变量绕过。

### 第二步：创建 Agent 基础配置

1. 创建一个多报告 Agent，名称建议为“知行市场研究 Agent”。
2. 配置统一系统规则：来源优先级、非个人化边界、风险提示、结构化输出、HTML/PDF 流程和日志脱敏。
3. 创建受控的 `report_type` 路由，分别加载六类报告模块。
4. 配置非敏感判断台账的读写边界与版本规则。

**通过条件**：能用固定的模拟请求选择正确报告模块；未知类型失败关闭，不输出自由文本猜测结果。

### 第三步：配置数据与报告模块

1. 按第 6 节逐一启用、测试并记录每个 Skill 的可用性。
2. 写入六类报告的固定结构和验收检查清单。
3. 为行业跟踪配置十六赛道清单及其已有深度报告的更新规则。
4. 为午间、每日、月末复盘配置判断台账的引用和验证规则。

**通过条件**：六类模拟报告均有可公开来源、日期、版本、风险提示和无个人数据正文。

### 第四步：配置 HTML 与 PDF

1. 生成受控 `content_html`。
2. 用 Playwright + Chromium 生成 PDF，并验证中文字体、表格、来源链接和分页。
3. 将 HTML、PDF、结构化 JSON 和生成状态作为同一次报告产物保存。

**通过条件**：每类报告至少一份 PDF 与 HTML 内容一致；PDF 失败能明确报错且不影响 HTML 校验。

### 第五步：配置 Calendar 验证日程

1. 按第 4 节创建六条独立 Calendar 日程及其 `time_range`。
2. 每条任务先检查交易日/节假日/月末条件，未满足时安全退出并记录原因。
3. 在月末重叠窗口进行一次并发/隔离测试。
4. 此阶段只产出 Coze 内部草稿，不连接正式应用推送。

**通过条件**：不误触发、不生成空报告、同一日程不重复生成、月末并发不串内容。

### 第六步：内容和接口验收

1. 每种报告提交一份完整样例，使用公开或明确标注为模拟的数据。
2. 先按内容标准验收结构、来源、时效、风险提示、标的池和 PDF。
3. 再与知行技术契约映射，验证严格 JSON、错误对象、版本和 API 部署能力。
4. API 验收只能在隔离环境完成，不接入用户、数据库、归档、发布、通知或真实 Token。

## 10. 验收清单

### 10.1 内容验收

- [ ] 六类报告均按约定日期/时区生成，且符合实际交易日规则。
- [ ] 所有关键结论都能追溯到真实来源与数据截至时间。
- [ ] 早盘、午间、复盘之间的判断验证可追溯，不篡改原判断。
- [ ] 行业跟踪不会每天重复长篇研究；深度更新有触发依据和版本号。
- [ ] 节假日和月末报告不包含个人持仓、交易、盈亏或操作归因。
- [ ] 标的池只含 A 股，且使用研究观察、风险和公开依据表述。
- [ ] 全部正文含固定风险提示；没有收益承诺或个性化交易指令。

### 10.2 技术与安全验收

- [ ] 交易日、节假日和月末判断均可核验，未采用简单工作日判断。
- [ ] 所有已使用 Skill 均经实际调用验证；缺失 Skill 有明确降级或阻断结论。
- [ ] HTML 与 PDF 成功生成，中文、表格和链接可读。
- [ ] PDF 失败不伪造成功、不阻塞 HTML 结果的安全处理已验证。
- [ ] Calendar 日程配置 `time_range`，并完成月末重叠日程的并发隔离测试。
- [ ] 不读取或写入 Token、`SECRET.md`、用户数据、持仓、交易记录或旧应用同步脚本。
- [ ] API 输出可映射到严格 JSON 契约；新增报告类型已有对应契约与样例。

|---|---|
| Coze Agent API 的 `/async_run` 在隔离 POC 中返回 `NotImplementedError` | 不使用它作为正式通道；不重复无目的测试。 |
| `/stream_run` 已通过固定内容 POC，但未完成真实报告可靠性设计 | 只作为候选；不直接接入正式归档。 |
| Calendar 是否可稳定调度一个可部署 Agent | 在创建日程前实测；失败后记录能力限制，不使用不安全替代方案。 |
| Skill 名称、权限和可用性可能变化 | 逐个实测，禁止仅凭交接文档假设可用。 |
| 20:00 行业跟踪与 20:30 月末复盘可能并发冲突 | 必须先做隔离测试；失败时改为月末 21:00 并请用户确认。 |
| 新增报告类型尚未进入正式契约 | 在 API 接入前更新 [coze-report-output-standard.md](./coze-report-output-standard.md) 与 [coze-report-contract.md](./coze-report-contract.md)。 |
| 曾出现在聊天中的 Token | 视为已暴露；正式接入前由用户在受控平台自行轮换，绝不粘贴到聊天、Prompt、日志或文档。 |

## 12. 本计划之后的执行顺序

1. 用户审阅并确认本计划。
2. 先更新报告内容标准和技术契约中的新增报告类型与样例要求。
3. 在 Coze 编程创建 Agent，并完成能力、Skill、HTML/PDF 和工作区核验。
4. 创建六条仅用于草稿验证的 Calendar 日程，完成模拟/公开数据验收。
5. 输出完整样例包，进行内容验收与 API 兼容性验收。
6. 仅在正式 Agent 调用路线、可靠性和安全边界明确后，进入知行应用工程阶段。
