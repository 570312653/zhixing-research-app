# 知行：报告内容输出标准（生成引擎无关）

> 状态：仍为有效的内容与业务字段标准；生成责任已从 Coze 改为未来的“知行报告引擎”。Coze 相关实现与调用契约已归档，不得作为本标准的前置条件。  
> 版本：v0.3  
> 最后更新：2026-07-28  
> 配套架构文档：[report-engine-architecture.md](./report-engine-architecture.md)

## 1. 目的与使用方式

本文件规定报告生成引擎对“知行”交付的**内容质量、报告结构和业务字段语义**。它用于确认真实报告模板，不负责定义 API 鉴权、调用地址、重试或数据库实现。

应按下面的顺序使用：

1. 报告引擎为每一类报告提交一份完整、可阅读的固定样例，以及对应的结构化交付对象。
2. 你确认内容质量、栏目、口径和语气。
3. 知行再将确认后的样例与正式报告引擎技术契约一起做技术交付验收。

本文件不是投资建议，也不要求报告引擎执行定时任务、访问用户数据、发送通知、写入数据库或处理应用权限。

## 2. Agent 的责任边界

### 2.1 报告引擎必须负责

- 基于用户维护的报告模板、研究逻辑和允许的数据来源，生成报告内容。
- 按本文件的报告结构输出清晰、可追溯、带风险提示的内容。
- 为每份报告提供结构化元数据、版本号、数据截至时间和来源链接。
- 对无法确认的信息明确标注“待核实”“未获取到可靠来源”或不写入结论。
- 对核心关注标的池输出独立的完整快照，不从正文中让应用猜测标的变动。

### 2.2 报告引擎不得负责

- 用户注册、登录、订阅、权限判断或用户分层。
- 站内通知、邮件、短信、微信推送或对外消息发送。
- 应用的发布、撤回、归档、版本覆盖、重试、幂等或审计决策。
- 获取、保存、展示或输出任何 API Token、密码、Cookie、个人隐私数据或内部 Prompt。
- 代替持牌机构向特定用户给出个性化买卖指令、收益承诺或保证盈利表述。

## 3. 通用内容标准

### 3.1 内容原则

- 以“帮助读者在 5～10 分钟内理解市场变化、主线和风险”为目标，先结论、后依据。
- 区分**事实、数据、推断和观点**：不能把推断写成已发生事实。
- 结论必须与正文证据一致；不允许只给情绪化判断或标题党结论。
- 对时效敏感的信息写明数据截至时间；过期信息不得伪装为实时信息。
- 报告可使用专业术语，但首次出现时应尽量用简短中文说明。
- 正文以中文简体为主；证券代码、公司名称、指数和来源名称按原始规范保留。

### 3.2 来源与事实要求

- 重要数据、政策、公告、事件和引用判断应附可公开访问的来源链接，或明确说明来源不可公开。
- 不得虚构新闻、公司公告、价格、研报、数据、链接、分析师观点或引用。
- 对单一来源、传闻、未证实消息，必须写明不确定性，不能作为核心结论的唯一依据。
- 来源链接应尽量指向原始出处，例如交易所公告、公司公告、政府/监管机构、上市公司官网、公开媒体或正式研究资料。
- 如来源受版权、订阅或访问限制，正文只概述必要事实，不复制长段受版权保护内容。

### 3.3 风险提示与合规表达

每份报告的正文末尾必须原样包含：

> 仅供信息参考，不构成投资建议。

不得出现或变相表达：

- “保证上涨”“稳赚”“确定性收益”“闭眼买入”等收益承诺；
- 面向某位用户的买入、卖出、仓位、止损或资金配置指令；
- 将核心关注标的池描述为“荐股池”“推荐池”或保证性名单；
- 隐去重大不确定性、数据时点或与结论相反的重要事实。

### 3.4 标题、日期与版本

- 标题必须包含：报告名称、报告日期、版本号。
- 版本格式为 `v主版本.次版本`，首版固定从 `v1.0` 开始；内容修订后依次为 `v1.1`、`v1.2`。
- `report_date` 表示报告归属日期；`generated_at` 表示生成完成时间；二者不得混用。
- 所有结构化时间使用带时区的 ISO-8601；面向用户展示时以 `Asia/Shanghai` 为准。
- 早盘、午间复盘、每日复盘、行业跟踪和月末复盘必须使用 A 股实际交易日历；节假日摘要必须使用连续休市最后一天规则，不得仅按周一至周五或自然月末判断。

### 3.5 正文格式

- 应用默认阅读载体为安全的 HTML 正文；PDF 可以作为可选下载附件，不能替代正文交付。
- 正文必须有清晰层级。允许的元素仅限 `h2`、`h3`、`p`、`ul`、`ol`、`li`、`strong`、`em`、`a`、`table`、`thead`、`tbody`、`tr`、`th`、`td`、`blockquote`、`br`、`hr`；链接仅允许安全的 `https` 地址。
- 不使用内嵌脚本、iframe、表单、追踪像素、外部样式表、事件属性或任何可执行内容。
- 图表如需使用，应提供可公开访问的图片地址、图表说明、数据时间和来源；没有可靠图表时宁可不放。
- 段落宜简洁。单个要点优先说明“发生了什么 → 为什么重要 → 对 A 股/行业观察意味着什么 → 风险或待验证点”。
- PDF 必须由通过内容校验的 HTML 使用 Playwright + Chromium 导出；不得用 reportlab 直接拼版。PDF 失败时如实写入产物状态，不得伪造成功，且不能替代 HTML 正文交付。

## 4. 统一结构化交付对象

报告引擎在技术接入前，应先以 JSON 样例提交下列对象。本节只定义业务内容字段的含义；新引擎的调用和错误契约将在实现前另行建立，不复用 Coze 的 API、SSE 或异步路径。

```json
{
  "schema_version": "1.0",
  "delivery_id": "唯一交付编号",
  "delivery_type": "report",
  "request_id": "一次生成请求编号",
  "report_id": "稳定报告编号",
  "report_type": "morning_scan",
  "report_date": "2026-07-22",
  "version": "v1.0",
  "title": "知行｜早盘扫描｜2026-07-22｜v1.0",
  "summary_points": ["不超过 5 条的核心摘要"],
  "content_html": "<h2>...</h2>",
  "market_scopes": ["us_equities", "global_futures"],
  "industry_tags": [],
  "theme_tags": [],
  "source_links": [],
  "pdf_artifact": {
    "status": "succeeded",
    "file_name": "知行-早盘扫描-2026-07-22-v1.0.pdf",
    "mime_type": "application/pdf"
  },
  "data_as_of": "2026-07-22T08:45:00+08:00",
  "generated_at": "2026-07-22T08:50:00+08:00"
}
```

### 4.1 字段要求

| 字段 | 要求 |
|---|---|
| `schema_version` | 当前首版为 `1.0`；字段语义或类型不兼容变更时升级主版本。 |
| `delivery_id` | 每一次交付唯一，不可由应用补造。 |
| `delivery_type` | 报告使用 `report`；标的池完整快照使用 `watchlist_snapshot`。 |
| `request_id` | 对应一次生成请求；必须原样回显。 |
| `report_id` | 同一报告的稳定标识；修订版本不得随意更换。 |
| `report_type` | 只能为 `morning_scan`、`midday_review`、`daily_review`、`industry_tracking`、`holiday_digest`、`month_end_review`、`industry_research`。 |
| `report_date` | `YYYY-MM-DD`；按报告归属日而非上传日填写。 |
| `version` | `v1.0`、`v1.1` 等格式。 |
| `title` | 必须可直接展示，含类型、日期、版本。 |
| `summary_points` | 3～5 条；每条应是可独立理解的结论，不能只写口号。 |
| `content_html` | 完整可阅读正文，含固定风险提示。 |
| `market_scopes` | 报告覆盖市场的受控数组，见各类型规则。 |
| `industry_tags` | 产业报告使用申万一级行业；其他报告没有时返回空数组。 |
| `theme_tags` | 可选主题标签；没有时返回空数组。 |
| `source_links` | 重要来源数组，格式见下节；没有可公开来源时返回空数组并在正文说明。 |
| `pdf_artifact` | 可选 PDF 产物元数据；只含 `status`、文件名和 MIME 类型，不得携带本地绝对路径、Token 或不受控公开链接。`status` 只能为 `succeeded`、`failed`、`not_requested`。 |
| `data_as_of` | 本次内容数据截至时间。 |
| `generated_at` | 报告引擎生成完成时间。 |

### 4.2 `source_links` 的统一格式

```json
[
  {
    "title": "来源标题",
    "publisher": "发布机构或媒体",
    "url": "https://example.com/source",
    "published_at": "2026-07-22T08:00:00+08:00",
    "source_type": "company_announcement",
    "context": "该来源支持的事实或数据点"
  }
]
```

- `url` 必须为完整 HTTPS 链接；无法公开访问时不伪造链接。
- `published_at` 不确定时可为 `null`，但 `title`、`publisher`、`url`、`context` 仍须真实且完整。
- `source_type` 推荐使用：`company_announcement`、`exchange`、`regulator`、`government`、`market_data`、`news_media`、`research`、`other`。

## 5. 各类报告内容标准

### 5.1 早盘扫描 `morning_scan`

**定位**：为 A 股开盘前提供外围市场背景，不是只覆盖 A 股。

**市场范围**：至少按当日实际可得信息覆盖美股、全球期货/大宗商品、重要汇率或宏观风险事件；可根据模板补充其他外围信息。`market_scopes` 至少包含与实际正文一致的项目，例如 `us_equities`、`global_futures`、`commodities`、`fx`、`macro`。

**推荐正文结构**：

1. 开盘前一句话判断：说明需要重点观察的风险或主线，不给交易指令。
2. 隔夜市场速览：美股主要指数、关键行业/资产、显著事件。
3. 期货与大宗：与 A 股相关的能源、金属、农产品或指数期货变化及原因。
4. 宏观、政策与地缘风险：仅列有证据且可能影响当天风险偏好的事项。
5. 映射到 A 股的观察方向：写“关注/可能影响/待验证”，不能把关联写成确定涨跌。
6. 当日风险日历：关键数据、会议、公告或事件的时间点（如有）。
7. 风险提示。

**质量门槛**：

- 数据截至时间通常不晚于 A 股交易日 08:45 左右；若明显延迟必须在正文和元数据中如实体现。
- 摘要应突出 3～5 个最重要变量，不能堆砌盘点。
- 对隔夜上涨/下跌必须尽量说明驱动因素或标注驱动未明。

### 5.2 午间小复盘 `midday_review`

**定位**：仅复盘 A 股上午盘面，并对上一交易日每日复盘、当日早盘扫描中的可验证市场判断做非个人化验证。

**市场范围**：`market_scopes` 固定至少包含 `cn_a`。盘前外围信息只能作为“与早盘判断的对应关系”出现，不得取代上午 A 股事实。

**推荐正文结构**：

1. 上午市场概览：主要指数、量能、广度、板块与显著异动。
2. 与早盘扫描的对应关系：明确哪些信号得到支持、出现背离或尚待下午验证。
3. 市场判断验证表：逐条引用原判断的报告日期、报告 ID、原判断、可公开证据和状态。
4. 午后观察清单：仍需验证的变量、事件与风险，不给个人化交易指令。
5. 风险提示。

**质量门槛**：

- 验证状态只能是“已验证”“部分验证”“未验证”或“失效”；不能事后改写原判断。
- 每条验证必须保留原报告 ID 和日期；没有可公开证据时标注“未验证”，不能凭印象补结论。
- 不读取或讨论用户持仓、交易、盈亏或操作记录。

### 5.3 每日复盘 `daily_review`

**定位**：仅复盘 A 股当日市场，不混入未标注的海外市场结论。

**市场范围**：`market_scopes` 至少包含 `cn_a`，且除非明确作为背景，不应将海外市场作为正文主体。本地固定样例的结构化输出固定为 `['cn_a']`。

**判断验证**：每日复盘必须显式接收并验证同日 `morning_scan` 与同日 `midday_review` 的前序判断；不得以同日 `daily_review` 自引用。每条判断必须保留报告 ID、报告日期、原判断、状态和结构化验证证据；仅“未验证”状态可没有验证证据，其余状态必须至少有一条合格证据。每日复盘的 `data_as_of`（引擎请求字段为 `dataAsOf`）必须由调用方显式提供，不得从来源或模型推断。

**推荐正文结构**：

1. 一句话总览：指数、量能、风险偏好与市场主线的当日特征。
2. 市场表现：主要指数、成交额/量能、涨跌家数或其他已验证的广度指标。
3. 主线与板块：领涨/领跌或关键分化，说明催化、持续性与证据。
4. 重要事件与公告：只列对市场理解有实质影响的事项。
5. 情绪与结构观察：例如高低位切换、资金偏好、题材扩散/收缩；必须区分事实与推断。
6. 当日判断验证表：列出同日早盘和午间判断、验证状态及其结构化证据，不事后改写原判断。
7. 次日观察清单：需验证的事件、数据、板块或风险，不给个性化交易指令。
8. 风险提示：正文末尾必须原样包含“仅供信息参考，不构成投资建议”。

**质量门槛**：

- 数据截至时间通常不早于 A 股收盘后的整理完成时点；若为盘中版必须在标题和正文清楚标记。
- 不得把“板块上涨”直接等同于“后续必涨”。
- 对个股案例仅用于说明市场结构，必须有公开来源、日期和风险说明。
- 固定样例不接入真实数据、网络、模型或交易日历；它只验证固定夹具的格式、来源结构、前序判断关系和输出合规，不能被解释为真实市场报告。

### 5.4 行业跟踪 `industry_tracking`

**定位**：A 股交易日 20:00 的十五五产业赛道跟踪日报，不等同于每天重新生成一份完整深度研报。

**行业与标签**：

- `industry_tags` 使用申万一级行业；`theme_tags` 可补充十五五赛道、产业链、技术路线或政策主题。
- 每日覆盖赛道总览、显著变化、催化、资金/轮动、观察标的池变化和风险。

**推荐正文结构**：

1. 赛道变化总览：当日强弱、资金、异动与显著轮动。
2. 变化原因与证据：区分事实、推断和仍待核实的因果解释。
3. 催化、风险与观察节点。
4. 核心关注标的池的研究观察变化；只写公开依据、风险和条件，不写买卖或仓位指令。
5. 深度研究更新（仅在政策、供需、业绩、技术路线、产业链或监管出现重大变化时追加）。
6. 风险提示。

**质量门槛**：

- 不能以每日长篇重复代替跟踪；没有重大变化时应简明说明“无新增深度结论”。
- 深度更新必须引用已有报告 ID 和版本；首次深度研究使用 `industry_research`，后续同主题修订提升版本号。

### 5.5 节假日资讯摘要 `holiday_digest`

**定位**：在周末、法定假日等连续休市期间的最后一天晚上，筛选可能影响下一交易日的高价值新闻与信息。

**市场范围**：按实际内容填写，通常可包含 `cn_a`、`us_equities`、`global_futures`、`commodities`、`macro` 等。

**推荐正文结构**：

1. 假期信息总览：本次连续休市区间与下一交易日。
2. 高优先级新闻：按“影响级别 + 事实 + 来源 + 可能影响”表达。
3. 海内外政策、宏观、行业与公司事件。
4. 假期市场变化：仅在有可靠数据和明确时间范围时列入。
5. 开市前待验证事项与风险。
6. 风险提示。

**质量门槛**：

- 不是假期新闻流水账；只保留对下一交易日或后续一段时间有潜在影响的信息。
- 必须标注新闻发生时间，避免把假期早期已失效的信息置于首位。
- 若假期内无足够高价值事项，应如实输出简短摘要，不为凑篇幅编造“热点”。

### 5.6 产业研究 `industry_research`

**定位**：面向特定行业或主题的中短期研究归档；首版默认经人工审核后发布。

**行业与标签**：

- `industry_tags` 必须至少含一个申万一级行业。
- `theme_tags` 可补充产业链、技术路线、政策主题或事件主题。
- 如果跨行业，按主要研究对象列多个申万一级行业，不得用模糊的自造行业名称替代。

**推荐正文结构**：

1. 研究问题与核心结论：清楚说明本报告试图回答什么。
2. 行业/主题背景与关键变化。
3. 证据与数据：分点列出来源、时间和对结论的支持关系。
4. 产业链、竞争格局或供需变化（适用时）。
5. 可能受益/受压环节：以研究观察表述，不构成推荐。
6. 关键不确定性、反例与风险。
7. 后续跟踪指标或事件。
8. 风险提示。

**质量门槛**：

- 结论不能只基于单篇新闻或单个价格变化。
- 应明确研究覆盖的时间范围与数据截止时间。
- 如引用公司或证券，不能把“关注”写成“买入建议”；重点描述产业逻辑与不确定性。

### 5.7 月末复盘 `month_end_review`

**定位**：每月最后一个 A 股实际交易日的非个人化市场研究复盘，归因对象是市场与行业，不是任何用户的交易表现。

**市场范围**：`market_scopes` 至少包含 `cn_a`；如有外围背景，必须与 A 股主体明确区分。

**推荐正文结构**：

1. 当月市场总览：主要指数、风格、量能、风险偏好和主线演变。
2. 行业与赛道归因：结构性强弱、政策/宏观变量及其证据。
3. 月内市场判断验证：引用原报告 ID，汇总“已验证/部分验证/未验证/失效”的公开证据。
4. 下月观察框架：关键数据、政策、产业催化与风险变量。
5. 风险提示。

**质量门槛**：

- 不得读取或输出个人持仓、买卖、盈亏、仓位、操作归因或再平衡建议。
- 不把月度涨跌简单归为单一原因；原因不确定时必须说明不确定性。

## 6. 核心关注标的池快照标准

核心关注标的池是可追溯的研究观察清单，不是荐股池。它必须作为独立 `delivery_type: "watchlist_snapshot"` 完整交付，不能只散落在报告正文中。

### 6.1 快照对象

```json
{
  "schema_version": "1.0",
  "delivery_id": "唯一交付编号",
  "delivery_type": "watchlist_snapshot",
  "snapshot_id": "稳定快照编号",
  "snapshot_version": "v1.0",
  "snapshot_at": "2026-07-22T18:00:00+08:00",
  "items": [
    {
      "security_code": "000001.SZ",
      "security_name": "示例名称",
      "market": "cn_a",
      "industry_tag": "申万一级行业",
      "status": "active",
      "first_mentioned_at": "2026-07-22",
      "last_mentioned_at": "2026-07-22",
      "attention_reason": "研究观察原因摘要",
      "risk_notice": "与该观察相关的主要风险",
      "removal_reason": null,
      "evidence": [
        {
          "title": "关联公开来源标题",
          "url": "https://example.com/source"
        }
      ]
    }
  ]
}
```

### 6.2 快照规则

- 仅纳入 A 股标的，`market` 固定为 `cn_a`。
- 每次交付必须包含当时的**完整当前清单**，而不是仅传新增或删除项。
- 每个标的至少包含证券代码、名称、申万一级行业、状态、首次/最近提及日期、关注原因、风险提示和关联依据。
- `status` 只可为 `active` 或 `removed`。`new` 与 `ongoing` 由应用比较相邻快照后派生，不能由报告引擎代替判断。
- 本次仍在关注的标的以 `active` 交付；首次移出的标的以 `removed` 交付，并填写非空 `removal_reason`。应用归档移出记录后，后续快照可不再包含该标的。
- 应用负责比较相邻快照、形成新增/持续/移出轨迹，并在灰度期由管理员审核后发布。
- 所有涉及标的的表述都必须使用研究观察语言，不得构成具体投资建议。

## 7. 报告引擎首轮样例包要求

在开始 API 交付层确认前，报告引擎应一次性提交下列内容。样例必须使用公开或模拟但明确标注的数据；不得使用 Token、用户信息或私有凭证。

1. 一份完整早盘扫描样例：包含 JSON 对象、可阅读 HTML 正文和 PDF 产物状态。
2. 一份完整午间小复盘样例：包含可追溯的早盘/前一日复盘判断验证表。
3. 一份完整每日复盘样例：包含 JSON 对象和可阅读 HTML 正文。
4. 一份完整行业跟踪样例：包含赛道变化、来源、风险和一次“无新增深度结论”或版本化深度更新。
5. 一份完整节假日资讯摘要样例：包含 JSON 对象和可阅读 HTML 正文。
6. 一份完整月末复盘样例：只包含非个人化市场研究和可追溯的判断验证。
7. 一份完整产业研究样例：至少含一个申万一级行业和来源链接。
8. 一份完整核心关注标的池快照样例：至少 3 个模拟或公开可验证的 A 股标的，并明确标注为测试样例。
9. 每类样例对应的“生成失败/输入不完整”结构化错误样例；错误中不得带 Prompt、Token、完整正文或内部堆栈。
10. 字段映射说明：报告模板的每个主要栏目分别写入哪个 JSON 字段或 HTML 小节。

## 8. 用户验收清单

你可逐项检查；任一“必须通过”项不满足，就先调整报告引擎的模板、数据适配或输出逻辑。

### 8.1 通用验收

- [ ] 每份样例的标题含日期和版本号。
- [ ] 报告类型、报告日期、数据截至时间、生成时间齐全且语义正确。
- [ ] `summary_points` 为 3～5 条真正的核心结论。
- [ ] 正文有清晰层级，并含固定风险提示。
- [ ] 重要事实和数据有真实、可打开或明确受限的来源。
- [ ] 没有虚构来源、收益承诺、个性化交易指令或内部 Prompt。
- [ ] HTML 可直接阅读，不含脚本、表单或不可控嵌入。
- [ ] 版本格式、日期格式、报告类型枚举与本文件一致。

### 8.2 分类验收

- [ ] 早盘扫描确实覆盖外围市场，并清楚解释其与 A 股开盘的关系。
- [ ] 午间小复盘的验证记录可追溯到原报告 ID、原判断和公开证据。
- [ ] 每日复盘以 A 股为主体，能说明市场结构和次日待验证事项。
- [ ] 行业跟踪覆盖受控赛道，且不会把每日跟踪伪装成重复的深度研究。
- [ ] 节假日摘要只保留高价值信息，并说明假期区间和下一交易日。
- [ ] 月末复盘仅归因市场、行业和风格，不包含个人交易或持仓信息。
- [ ] 产业研究含申万一级行业、研究问题、证据、反例/风险和跟踪指标。
- [ ] 标的池是独立完整快照，字段齐全，仅含 A 股且没有“荐股”表述。

### 8.3 通过标准

首轮内容验收通过，至少意味着：

- 八类样例（七类报告 + 标的池快照）均完整可读；
- 字段没有依赖应用“猜测补齐”；
- 你认为报告模板、语气、信息密度和风险表述可以作为灰度期基线；
- 报告引擎能说明字段变更时会先与知行更新版本与样例，而不是静默改格式。

## 9. 内容变更规则

- 修改文风、增加可选栏目、补充正文内容但不改变字段含义时，可保持 `schema_version` 不变，并按需要提升报告 `version`。
- 删除必填字段、改变字段类型、改变报告类型语义或修改标的池状态枚举时，必须先与知行确认，并升级 `schema_version` 主版本。
- 每次重大模板调整至少提交一份新旧样例对比，说明影响的报告类型、字段和阅读体验。
- 未经确认，报告引擎不得静默改为 PDF-only、纯自然语言输出，或将关键字段隐藏在正文中。

## 10. 当前未决项

以下项目不阻碍报告引擎先提交内容样例，但必须在进入正式 API 接入前确认：

- 每类报告允许的数据源范围与版权/授权边界。
- 早盘、复盘、节假日摘要的“最晚可接受生成完成时间”。
- 产业研究的人工审核人及审核通过标准。
- 是否保留 PDF 下载，以及 PDF 的生成、存储和受控访问方案。
- 正式 Agent 是否复用现有成熟模板，及其可验证的部署/API 能力。
- 正式调用采用同步还是异步机制、轮询方式、超时、重试和取消语义；当前 Coze 隔离 POC 的 `/async_run` 不可用，不得作为新引擎的默认方案或实现依据。
